# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter app (package name `work_hu`, product name "DukApp") for tracking a local PACE/MyShare competition: user status, activities, transactions, payments/donations, top-ups, a "bufe" (kiosk) with SumUp payments, camps, mentors/mentees, and admin tooling. Targets Android, iOS and web (web renders inside a 500px phone-sized frame via `flutter_web_frame`).

## Commands

```bash
flutter pub get
flutter run                     # add -d chrome for web
flutter analyze                 # lints: flutter_lints (see analysis_options.yaml)
dart run build_runner build --delete-conflicting-outputs   # regenerate *.freezed.dart, *.g.dart, locator.config.dart
flutter build apk | flutter build ios | flutter build web
```

There is no `test/` directory yet (`flutter_test` and `mocktail` are available). Single test: `flutter test test/path_test.dart --plain-name "name"`.

Run `build_runner` after changing any `@freezed` / `@JsonSerializable` class or any `@singleton` / `@lazySingleton` / `@injectable` annotation. Never hand-edit generated files.

## Architecture

**Entry:** `lib/main.dart` → `setupLocator()` (get_it + injectable, `lib/app/locator.dart`) → `ProviderScope` → `DukApp` (`lib/dukapp.dart`). `DukApp` waits on `authInitProvider`, then builds `MaterialApp.router` with `routerProvider`, theme and locale providers.

**Two DI systems coexist:**
- **get_it/injectable** for app-wide singletons: HTTP clients in `lib/api/` (`DioClient`, `BufeClient`, `GMClient`) and `UserProvider`. Accessed via `locator<T>()`.
- **Riverpod 3** (mostly the legacy `StateNotifierProvider` API from `flutter_riverpod/legacy.dart`) for feature state. `userDataProvider` wraps the get_it `UserProvider` singleton so the router can listen to it.

**HTTP / auth** (`lib/api/dio_client.dart`): the base URL is hard-coded (`_baseUrl`; a commented LAN alternative sits next to it). A `QueuedInterceptorsWrapper` attaches the JWT and, on 401/403, calls `/auth/refreshtoken`, stores the new tokens (via `Utils.saveData`), and retries; if refresh fails it logs the user out. `main.dart` globally disables TLS certificate validation through `HttpOverrides`.

**Feature layout** (`lib/features/<feature>/`), layered as:
- `data/api/*_api.dart` – raw Dio calls through `locator<DioClient>()`, returns `res.data`
- `data/repository/*_repository.dart` – maps JSON to freezed models, `PaginatedResponse<T>` for lists
- `data/model/` – freezed + json_serializable models; `data/state/` – freezed page state
- `providers/` – declares `xApiProvider` → `xRepoProvider` → `xDataProvider` (a `StateNotifierProvider.autoDispose`)
- `view/` and `widgets/` – UI

Folder names are not fully consistent (`provider` vs `providers`, `widget` vs `widgets`), so check the existing folder before adding files.

**Base framework** (`lib/app/framework/base_components/`, `lib/app/providers/base_provider.dart`):
- Notifiers extend `BaseDataNotifier<S>` and implement `copyWithState(BaseState)`. All API calls go through `executeApiCall<T>(call, onSuccess:, onError:)`, which sets `ModelState` (loading/success/error/empty), shows or hides the global `LoadingScreen` overlay (needs `navigatorKey.currentContext`), and converts errors to i18n messages.
- List screens: the notifier implements `ListApiProvider<F>` (`list({filter, page, size, sort})`), state holds a `BaseListState` (paging info), and the page extends `BaseListPage` / `BaseListPageState<P, S, N>`, which handles infinite scroll paging. Pages that aren't lists extend `BasePage` / `BasePageState`. Build sort params with `SortBuilder`. The paging convention is: page 0 replaces the list, later pages append.
- Shared UI widgets (dialogs, chips, list items, search bar, etc.) live in `lib/app/widgets/`.

**Routing** (`lib/app/providers/router_provider.dart`): a single GoRouter using `StatefulShellRoute.indexedStack` with branches (balance/home, status, jobs, profile, admin; the bottom nav items follow this order), with sub-routes nested under them. `redirect` sends users to `/login` unless the route is public (`/login`, `/tos`, `/privacy`, `/donate…`), and forces `/change-password` when `user.changedPassword` is false. Users without a church (`UserModel.churchId` null, sent by the backend's `UserDto`) only get the balance and profile tabs: `ScaffoldWithNestedNavigation._tabs` hides the rest (bar items carry their branch index, since hidden tabs leave gaps) and `redirect` sends `/`, `/status`, `/jobs` and `/admin…` to `/balance`. The router refreshes on `UserProvider` changes. New pages must be registered here.

**Roles:** `UserModel` (in `features/login/data/model/`) has role helpers such as `isAdmin()`. Providers use them to scope queries (e.g. non-admins are filtered to their own id).

**Roles and permissions:** a user has several roles (`UserModel.roleNames`) and the backend sends the union of their permissions as `UserModel.permissions` (names, so permissions this app doesn't know yet don't break parsing). Check access with `user.hasPermission(Permission.X)` (enum in `lib/app/models/permission.dart`, mirrors the backend), not with `role`. `role` is only the legacy single role the backend derives. Roles are managed in `lib/features/roles/` (admin → Roles, needs `ROLE_MANAGE`; the ADMIN role is read-only, built-in roles can't be renamed or deleted) and assigned to users in `UserDetails` via `PUT /user/{id}/roles`. The admin page and the bottom nav (`UserModel.hasAdminAccess()`) show entries by permission; admins keep seeing everything. The backend stays the authority: the UI only hides what the user couldn't do anyway.

**Jobs (pre-registration):** `lib/features/jobs/`. A job exists before it happens; people register (with a comment), there is a registration and cancellation deadline, an optional participant limit with waitlist, age limits and a gender restriction. Users register themselves, their spouse and (as adults with the same `familyId`) their children; `JOB_MANAGE_ALL` registers anyone, from the Jobs tab as well as the admin list. The responsible user (or `JOB_MANAGE_ALL`) completes the job with hours per registered user, which creates a normal activity that then follows the existing activity flow. Creating jobs needs `JOB_CREATE`. The Jobs tab (`/jobs`, `/jobs/:id`) is for registering, plus "complete" for the job's responsible person; creating, editing, cancelling, completing and registering anyone happen in admin → Jobs (`/admin/jobs`, `create`, `:id`, `:id/edit`, shown with `JOB_CREATE` or `JOB_MANAGE_ALL`). Both use `JobsPage` / `JobDetailPage` with a `manage` flag; `jobsDataProvider` is a family by that flag. Old `/profile/jobs…` links redirect to `/jobs…`. The repository wraps calls in `guardApi` (`lib/app/framework/api_exception.dart`) so the backend's plain-text reason (409 full, 422 deadline passed or not eligible) reaches the user: notifiers pass `onError: (m) => showApiError(m)` to `executeApiCall`.

**Audit log:** `lib/features/audit_log/`, admin → Audit log (needs `AUDIT_LOG_VIEW`, backend `GET /api/auditLog`). Newest first, filters for action, entity type, user, dates and free text; tapping an entry shows its details JSON. Action names are kept as strings and translated with `audit_action_<NAME>` (unknown ones show their raw name).

**Incomplete names:** when Google sends no last name the backend stores `-` and sets `UserModel.profileIncomplete`. `CompleteNameGate` (wrapped around the shell in `router_provider.dart`) then shows a small non-dismissible dialog asking for last and first name and saves it with `PUT /user/{id}`; it also appears for a restored session. The only way out besides saving is logging out.

**Sign in with Apple:** the login page shows the native "Sign in with Apple" button in the iOS app only (not on the web or Android), next to the Google button, as App Store rule 4.8 requires. `LoginDataNotifier.signInWithApple` sends the identity token and the name (Apple gives it only the first time) to `/auth/apple`; the iOS capability is the `com.apple.developer.applesignin` entry in `Runner.entitlements` and must be switched on for the App ID.

**Mailing:** admin → Mailing (`lib/features/mailing/`, needs `MAILING_SEND`) writes an e-mail to the members (users with `UserModel.member`, switched in the user details) in a `flutter_quill` rich text box, converts it to e-mail HTML (`vsc_quill_delta_to_html`, `ConverterOptions.forEmail()`) and sends it through `/api/mailing`, which cleans it again; "Send test to me" first, and a history of sent mailings.

**Streams:** admin → Streams (`lib/features/streams/`, needs `STREAM_MANAGE`) is the former Python tool for the website's live streams: start a Cloudflare live input by title (with a blinking "Audio felvétel!!" notice for 5 s), list the inputs with RTMPS address and stream key (key hidden until shown, copy buttons) and delete them. It only talks to the backend (`/api/streams`), which holds the Cloudflare credentials.

**Reading plan:** (only for users with the `READING_PLAN` permission: `readingPlanProvider` requests nothing and there is no card without it; the plan is requested in the app language with `?lang=`, the backend has the translations) a community reading challenge (first: the 150 psalms, 21 Oct - 13 Nov 2026) on the Home page: `ReadingPlanCard` (progress, this week's goal, pace; not shown without a plan) opens `PsalmsPage` (`/psalms`, a top-level route outside the tab shell so users without a church can open it too: tabs Read / Ranking / Challenge, a 5-column grid of the psalms with the current week's outlined, "Continue: next unread") and `PsalmReaderPage` (`/psalms/:n`: verses, previous/next, "I have read it" / undo). `readingPlanProvider` is optimistic (the mark changes at once and goes back with the reason if the server refuses; answers only replace the items when the last request is back). The psalm texts are bundled as one JSON file per translation in `assets/bible/` (`karoli_psalms.json` Károli 1908, `web_psalms.json` World English Bible, `kjv_psalms.json` King James Version, `luther1912_psalms.json` Lutherbibel 1912, `elberfelder1905_psalms.json` Elberfelder 1905, `norsk1930_psalms.json` Norsk Bibel 1930; all public domain, from github.com/midvash/bible-data `versions/<lang>/<slug>/books/Ps.json`, ~400 KB each, all 150 psalms) and listed in `bibleTranslations` (`bible_translation.dart`); `psalmTextProvider(translationId)` reads them, so reading works offline. The reader's translation button (`bibleChoiceProvider`, remembered in SharedPreferences) overrides the default, which follows the app language (`activeTranslationProvider`: first translation of that language, else Károli). To add a translation (it must be free to redistribute; the Hungarian psalm title counts as verse 1, so verse numbers differ from English in about 60 psalms): drop the file in `assets/bible/` and add an entry to `bibleTranslations`. Names in the ranking are full names (to be revisited, the users are mostly young).

**Reading plan articles:** a fourth tab "Cikkek" on `PsalmsPage` lists the published articles (+N pont, tick when read), `ArticleReaderPage` (`/psalms/article/:id`) shows the text read only (`ArticleBody`: a read-only `QuillEditor` over the stored delta; links only http/https/mailto) with "Elolvastam (+N pont)" / undo. Managers (`READING_PLAN_MANAGE`) get Admin → "Olvasási terv – cikkek" (`/admin/readingPlan`: list incl. drafts, `/new`, `/:id`): `ArticleEditPage` with title, points, a published switch and the same Quill toolbar/editor as the mailing page (pasting from Word keeps basic formatting); the body is stored as the delta JSON (`articleBodyOf` / `articleDocument`). Articles are translated: the Hungarian text is the article, `ArticleEditPage` has a language selector (`articleLanguages` in `article_languages.dart`: hu, en, de, nb; each language keeps its own draft while switching; a translation is saved on its own with `saveArticleTranslation`, points and the published switch only belong to Hungarian; translations need the saved article first) and readers get their app language (`articlesProvider`/`articleProvider` wait for `localeProvider`, `readingPlanProvider` waits too so nothing is requested in the wrong language), with a note when the text had to be Hungarian. The ranking now shows points (items + article points) with a "Zsoltárok: N · Cikkek: M pont" line. `LeaderboardModel` still reads an older backend's answer (no points fields).

**Bible:** (every signed-in user; the Bible card on Home, top-level routes outside the tab shell like `/psalms`) `lib/features/bible/`. `BiblePage` (`/bible`: "Continue: <book> <chapter>" at the last chapter opened, `biblePositionProvider`, remembered in SharedPreferences as `"John.3"`; a 5-column grid of the books' short names (`abbreviation` from the backend, e.g. "1Móz", "Ján"; shaded by group with `bookGroup`: law, history, poetry, prophets, gospels, Acts, Paul, other letters, Revelation; the book being read filled with the primary color) under Old/New Testament bars; a book opens to a grid of its chapters and a chapter to a grid of its verses on the same page (`bibleSelectedBookProvider`, `bibleSelectedChapterProvider`; back goes verses → chapters → books; one-chapter books go straight to their verses; a verse opens the reader at `?verse=n`, and back from the reader shows the chapters)) and `BibleChapterPage` (`/bible/:book/:chapter`, book = OSIS code such as `Gen`, `Ps`, `John`; previous/next and swiping cross into the neighbouring book); its title ("Róm 4 ▾") returns to the Bible page's book grid (book → chapter → verse): `BiblePage.showFrom` goes back to the Bible page when it is open (`BiblePage.openRoute`, also past the notes list), else the Bible page takes the reader's place (a reader opened from Home's "Continue"), so back from it returns where the reader came from. The full texts are not bundled: the backend lists them (`GET /bible/translations`, with `version` and download `size`; the list is remembered for offline, else the bundled `bibleTranslations` stand in, same ids) and sends one whole translation as gzipped JSON (`GET /bible/translations/{id}`, books → chapters → verses, same chapter/verse shape as the psalm files, book names in the translation's language). `bibleTextProvider(id)` shows the copy on the device at once, downloads when there is none (message with the size; failure message with retry, it then works offline), and downloads again in the background when the backend's `version` differs from the stored one; the parsed text stays in memory 2 minutes after the last screen closes. `BibleStore`: files on the phone (`<support dir>/bible/<id>.json.gz` + `<id>.version`, `bible_store_io.dart`), memory on the web (`bible_store_memory.dart`; the browser's HTTP cache answers there, the backend sends ETags). `BibleApi.getText` reads the answer as a stream so `DioClient`'s `LogInterceptor` doesn't print megabytes; parsing runs in an isolate (`compute`; tests pass `parse:` to `BibleRepository`). The translation pick is the same `bibleChoiceProvider` as the psalm reader (`bibleTranslationIdProvider`: pick, else the app language's default). **Parallel reading:** the reader's second app bar button (`BibleParallelButton`, "Párhuzamos olvasás") picks a second translation shown side by side (`bibleParallelChoiceProvider`, remembered as `bible_parallel`, empty = off; `bibleParallelIdProvider` is null when it equals the active translation); it is downloaded like the first. `_ParallelVerses` puts one row per verse number so the columns stay level (a verse one side lacks leaves its cell empty) and notes when the chapter's `numbering` labels differ (`BibleBook.numberingOf`, from the backend build: "heb" = a psalm whose title is verse 1, in Károli and Norsk; "kar" = Károli's own numbering; ...; rows then pair by number, not by content). Verse numbers are kept as in the text: WEB leaves out some verses and three verses are missing from the digital Károli, so don't assume 1..n. Tests: `test/features/bible/bible_test.dart`.

**Bible highlights, notes, bookmarks:** tapping verses in the reader selects them (frame) and swaps previous/next for `BibleSelectionBar` (`bible_annotation_widgets.dart`): five highlight colours and "no colour" in one row, then Note (`showNoteEditor` bottom sheet), Bookmark (on the first selected verse, toggles) and Copy (reference, verses, translation name to the clipboard). Highlighted verses get their colour as background (`highlightBackground`, softer in dark), bookmarks a small icon under the verse number, notes an icon at the end of their first verse that opens `showNotesSheet` (edit / delete). In parallel reading each column places the marks for its own chapter numbering; a tap on a row selects the active translation's verse. `/bible/notes` (`BibleAnnotationsPage`, bookmarks button on the Bible page) lists bookmarks, notes and highlights in Bible order; a tap opens `/bible/:book/:chapter?verse=n`, which scrolls to the verse and lights it up for 2 s. `bibleAnnotationsProvider` keeps them on the device in SharedPreferences per user (`bible_annotations_<userId>`: items, the queue of unsent changes, `next`, last sync), changes them there at once and syncs with `/bible/annotations` (on start and after each change: the queue is sent in order, then `GET ?since=next`; everything again when `next` is missing or the last sync is over 60 days old; a change the server refuses for good (400, 409, 413, 422: `refusedForGood`) is dropped; anything else waits in the queue, offline and above all 404, so a backend without these endpoints yet never costs people their notes). Every mark shows in every translation, placed by `shownRange` / `mapVerse` (`bible_annotation.dart`): the same `numbering` label keeps the verse; in the titled psalms "heb" verse n = "kjv" verse n-1 (the title, heb 1, = kjv 1); other pairs (Károli's own "kar" chapters, Norsk Dan 10, WEB Rom 14) keep the number and the verse says "jelölés Károli számozása szerint" (`VerseMarks.otherNumbering`); a mark past the chapter's end (Norsk runs some psalms' last verses together) goes to the last verse (`BiblePlace.lastVerse`). Highlight and bookmark act on the marks as shown (`shownAt`), so a mark made in another translation is changed or removed, never doubled; the list page shows verse text where the placement is exact. Ids are UUIDs from the `uuid` package. Tests in `test/features/bible/bible_test.dart` use `FakeAnnotationApi` (the backend's rules in memory) and `FakeUserProvider`.

**Share links:** the selection bar's Link copies the reference and `https://dukapp.bcc-ktk.org/bible/<OSIS>/<chapter>?verse=3` or `?verse=3-5` (`verseLink`); `/bible/:book/:chapter` reads the range with `parseVerseRange`, scrolls to it and lights it up. Links always open the Bible reader (open to every signed-in user), also from the psalm reader; signed-out users go through login and continue there (`DeepLink`). iOS opens them in the app because `web/.well-known/apple-app-site-association` lists `/bible*` and `/psalms*` (a web deploy, no app release); **Android app links don't verify yet**: `assetlinks.json` still has `REPLACE_WITH_RELEASE_SIGNING_SHA256_FINGERPRINT`, so links open the web app until the Play app signing key's SHA-256 is put there.

**Reading plan: marks and shared notes:** `PsalmReaderPage` uses the Bible's `BibleVerseTile` and `BibleSelectionBar` on the bundled psalm text, so highlights, notes, bookmarks, copy and link are the Bible's own (book `Ps`; numbering from `psalmNumbering` in `bible_translation.dart`: the 62 psalms whose title is verse 1 are "heb" in Károli and Norsk, as in the backend's files; book names from `psalmsBookName`). Church members (and READING_PLAN_MANAGE) also get **shared notes** (`/reading-plan/{id}/public-notes`): the bar's "Közös" writes one on the selected verses while the plan is open (the editor says everyone in the church sees it with the author's name), `PublicNotesSection` lists them under the psalm (author, verses, with the translation's short name when it numbers the psalm differently), the ⋮ menu edits / deletes your own, reports others' (`askReportReason`, once) and lets managers hide / show / delete; the psalm grid shows a small count badge (`publicNoteCountsProvider`). Users without a church see nothing and nothing is requested (`publicNotesAccessProvider`). Managers have Admin → reading plan articles → flag button → `ReportedNotesPage` (`/admin/readingPlan/reported`: reported notes with the reasons, open / hide / show / delete; it calls the API directly). Tests: `test/features/reading_plan/public_notes_test.dart` (`FakePublicNoteApi` with the backend's visibility rules).

**Navigation:** the tab shell (`router_provider.dart`, branches by index: 0 Home `/home`, 1 Status, 2 Balance `/balance`, 3 Jobs, 4 Admin, 5 Live; `_tabs` lists the visible ones in the bar: Home, Status, Balance, Jobs, Live while on the air, Admin). `/` and the start go to `/home`. **Home** (`features/start/view/start_page.dart`, `StartPage`): `LiveBanner`, `ReadingPlanCard`, `LocalStatusSection` (defined in `status_page.dart`, shown only on Home: the Status page starts with the user's own status) and the Bible card ("Folytatás: <label>" from `biblePositionProvider`, whose `label` is remembered as `bible_position_label`, so Home downloads nothing); users without a church only get the Bible card and their status is not requested. **Profile** is no tab: `ProfileAvatarButton` (initials) at the start of each tab's header (`BasePage.showProfileButton`, also Jobs as a tab but not from the admin, the Balance greeting and Live) opens `showProfileSheet` (`ProfilePage(inSheet: true)`: close button, no back button via `BasePage.showBackButton`). `/profile` (links, notifications) still opens the page, and its pages are top-level siblings with full paths (`/profile/activities`, `/profile/notifications`, `/profile/theme`, `/profile/language`, the old `/profile/jobs` redirect), so they open above the sheet. The sheet shows the name (and church), then "Személyes adatok" (`/profile/details`, `ProfileDetailsPage`: edits last/first name, gender and birth date with `PUT /user/{id}`; church, e-mail, phone and MyShare id read only; `UserModel.churchName` comes from the backend) and "Jelszó és biztonság" (`/profile/security`, `SecurityPage`: change the password with the current one, `POST /user/me/password`, at least 8 characters; it signs out every other device, this one sends its refresh token and stores the new access token from the answer; users who don't know theirs, e.g. Google/Apple sign-ins, can have a reset link e-mailed). **Password reset links:** "forgot password" on the login page, the security page and the admin's reset button in the user details (asks first, says where the link went or why it can't, e.g. no e-mail) all make the backend e-mail a one-time link to `/reset-password?token=...` (`ResetPasswordPage`, public route, also listed in the AASA for iOS): it checks the link, sets the new password, signs out locally and ends at the login page (the backend signs out every device). The reset calls go through `DioClient.plainDio`, so a stale local session can't log anyone out. Munkalapok (`/profile/activities`) and room booking are on Home (`_QuickLinks` in `start_page.dart`, church members only), not in the profile. `BaseListView` draws its own separators: don't put `Divider`s between its children (they doubled the lines in dark mode). The Balance page's header is the avatar plus its title (no greeting).

**SumUp payments (top-up, donation):** the checkout is created by the payment services (top-up: the Supabase function `sumup-create-checkout` via `BufeClient`; donation: `gm.bcc-ktk.org/checkouts` via `GMClient`, which gets a relative `redirect_url` and puts the web app's address in front) and opened with `CheckoutLauncher.open` (`lib/features/payments/`): the web app goes to SumUp in the same tab and comes back to `/balance/topUp/success/<ref>` or `/donate/<id>/success/<ref>`; the apps use the in-app browser (`LaunchMode.inAppBrowserView`: a Chrome Custom Tab on Android, where Google Pay works, unlike a plain WebView; Safari's in-app view on iOS, where Apple Pay works) and SumUp's `redirect_url` is `web/payment-return.html?to=<result route>` (`CheckoutLauncher.redirectUrl`), because a redirect never opens an app by itself: the page accepts only those two routes, opens `dukapp://app<route>` and offers a "back to DukApp" button and the web app as a fallback. The scheme is registered in `ios/Runner/Info.plist` (`CFBundleURLTypes`) and on Android by `PaymentReturnActivity` (intent filter `dukapp://app`; it starts `MainActivity` with CLEAR_TOP, which closes the Custom Tab, so `MainActivity` stays `singleTop`); go_router matches the link by its path. The result pages call `CheckoutLauncher.returned()` (forgets the pending checkout, closes Safari's view on iOS) and ask the service for the real status (failure page with "try again" when nothing was paid). Safety net while a checkout is pending (`CheckoutLauncher.pendingRoute`): on Android the result page opens when the app comes back to the front (the Custom Tab closed), on iOS (Safari's view doesn't pause the app) `PendingPaymentButton` ("Fizettem – fizetés ellenőrzése") under the pay button opens it. `<queries>` in the manifest lets url_launcher find Custom Tabs on Android 11+. Tests: `test/features/payments/checkout_return_test.dart` (the return link reaches the result pages).

**App updates (Android):** `AppUpdateChecker` (`lib/app/update/`, package `in_app_update`) asks Google Play for a newer version a few seconds after start and whenever the app comes back to the front (`main.dart`), at most every 6 hours; when there is one (and Play allows an immediate update) a dialog offers "Frissítés", which runs Play's own update screen (`performImmediateUpdate`) and restarts the app; "Később" is kept for that version until the next start; an interrupted update is carried on without asking. Only installs from Google Play get an answer (test tracks too); local builds, which are signed with the upload key and can't be updated by Play anyway, quietly get nothing. iOS has no such API (TestFlight / the App Store notify), the web neither. Tests: `test/app/app_update_checker_test.dart` (the decisions, with fake Play answers).

**Translations:** the `localization` package only replaces `%s` (in order) and `%s0`, `%s1`, ... (by index) in `lib/I18n/*.json`; `{0}` is NOT replaced and shows literally (a test checks that no text uses it).

**Admin tab visibility:** `UserModel.hasAdminAccess()` lists the permissions that show the Admin tab; when the admin page (`admin_page.dart`) gets an entry for a new permission, add it there too (a role with only that permission otherwise never sees the tab; `admin_access_test.dart`). **Rounds list:** shows every round (also old and inactive ones), so `RoundModel` must read rounds with empty optional columns (empty local goal = the main goal, empty `activeRound` = active); one unreadable row would otherwise break the whole list.

**Forms:** `BaseTextFormField` only runs its `validator` when `fldControl: "3"` is also passed (legacy behaviour; otherwise the validator is silently ignored), so set it on fields with a validator. The round form (`RoundEditPage`) also edits the Samvirk church status (percentage; empty = leave as it is).

**Users and rounds admin:** the users list has an "add user" button (`USER_MANAGE`, `UserCreateDialog`: the backend makes the username/MyShare id and e-mails a temporary password; a snackbar says whether the mail went out) and the user dialog now edits name, birth date, e-mail, phone, gender, member and roles, plus a delete button (`USER_MANAGE`, not for yourself) that asks first; the backend refuses users with history and the reason is shown. Rounds: `RoundsPage` lists all rounds (inactive ones greyed, "(inactive)") with a "+" button; `/admin/rounds/new` and `/admin/rounds/:id` open `RoundEditPage` (season, number 1-12, start/end/freeze dates, goals, active switch). Rounds cannot be deleted, deactivate them instead.

**Users without a church** (no Status, Jobs, Live or Admin tab) get Home with only the Bible card, the balance and the profile; their reading challenge card (for those who may see it) stays at the top of the profile. The live broadcast is for members only (users with a church): `liveStreamsProvider` asks nothing for others, the Live tab/banner stay away and `/live` is redirected like `/status` (to `/home`); the backend answers an empty list too. `/psalms` and `/bible` are top-level routes, open to them.

**iOS device family:** the iOS app is iPhone only (`TARGETED_DEVICE_FAMILY = 1` in `ios/Runner.xcodeproj/project.pbxproj`, no iPad orientations in `Info.plist`), after App Review (guideline 4) rejected the phone layout on iPad; it runs on iPads in iPhone compatibility mode. The centered-column layout for screens with a shorter side of 600 pt or more (`lib/dukapp.dart`) stays for Android tablets; on the web the app has its own 500 px frame. Making it a real iPad app would mean responsive layouts for every screen. The iPad icons in the asset catalog are harmless leftovers.

**Live viewing:** `liveStreamsProvider` (autoDispose, asks `/api/streams/live` every 15 s; any failure = nothing live) drives the Live tab (branch 5 in the shell, shown in the bar only while something is on the air or the tab is open; church users only), the `LiveBanner` on the Home page and `LivePage` (`/live`): one `ChoiceChip` per language (admin sets it per stream, `live_languages.dart`), the chosen language and "audio only" are remembered in SharedPreferences. The page keeps the chosen stream for 3 minutes after it drops out of the list (OBS reconnecting) while the player reconnects. Apps: `LivePlayer` plays the HLS address (it belongs to the live input, so it survives encoder reconnects) with `video_player`, or only the sound with `just_audio` + `just_audio_background` (lock screen controls, plays with the screen off: `JustAudioBackground.init` in `main.dart`, Android `MainActivity` extends `AudioServiceActivity` + service/receiver/permissions in the manifest, iOS `UIBackgroundModes` has `audio` (App Review once rejected it because the reviewer could not find a feature that needs it: the Live tab is for members and only exists while a stream is on the air, so when submitting show it with a demo member account, a running broadcast and a screen recording on a real iPhone; if it is rejected again, remove the entry and the sound stops in the background on iPhone)); a 4 s watchdog reopens the address when the position stands still or the player errors. The picture's fullscreen button opens `LiveFullscreenPage` (landscape, `SystemUiMode.immersiveSticky`; it shows the player's current connection through a `ValueNotifier`, so the watchdog's reconnects carry on, and closes when the player goes away); leaving puts portrait and `edgeToEdge` back. The app is otherwise portrait only (`main.dart`); iOS `Info.plist` lists landscape too, only so this page can turn. Web: browsers other than Safari can't play HLS, so it embeds Cloudflare's player page (`live_frame_web.dart`; audio only = the iframe shrunk to its control bar).

**Biometric unlock (apps only):** `lib/app/session/biometric_lock.dart` (`biometricLockProvider`, `local_auth`) puts Face ID / fingerprint (the phone's passcode as fallback) in front of a kept session. Switched on per device on the Password and security page (shown only when `available`: iOS/Android with biometrics enrolled; switching on needs one successful check and sets `keep_logged_in`), stored in secure storage as `biometric_lock`, deleted by `UserProvider.logout`. `authInitProvider` decides the lock before the first frame; `BiometricGate` (in `MaterialApp.builder`, above every route) covers the app while locked, prompts at once, relocks after `relockAfter` (5 min) in the background (`paused`/`hidden`, not `inactive`: the Face ID sheet makes the app inactive) and offers "Belépés jelszóval" (= logout). Platform setup: `NSFaceIDUsageDescription` in `Info.plist`; Android `USE_BIOMETRIC` and `MainActivity` extends `AudioServiceFragmentActivity` (local_auth needs a FragmentActivity, audio_service for the Live tab). **Android minimum is API 31 (Android 12)** (`minSdkVersion 31`), so the AppCompat launch theme local_auth needs on Android 8 and older isn't. Tests: `test/app/biometric_lock_test.dart`.

**Platform look:** the iOS app uses Cupertino widgets, Android and the web (also in an iPhone browser: `dukapp.dart` sets the theme platform to Android on the web) keep Material. `lib/app/platform/adaptive.dart` has the helpers: `useCupertino(context)`, `AdaptiveAlertDialog` (drop-in for `AlertDialog`, turns TextButton/FilledButton actions into Cupertino dialog actions), `pickDate` / `pickTime` (instead of `showDatePicker` / `showTimePicker`) and `AdaptiveSegmented` (instead of `SegmentedButton`). Switches, checkboxes, progress indicators and `RefreshIndicator` use their `.adaptive` constructors, and the bottom navigation is a `CupertinoTabBar` on iOS. New code should use these instead of the plain Material ones. Text fields, buttons and app bars stay Material on every platform.

**i18n:** the `localization` package loads JSON from `lib/I18n/` (`en_US.json`, `hu_HU.json`). Use `"key".i18n()`. Add every new key to both files.

**Sizing:** `flutter_screenutil` uses a 360×640 design size, so use `.w`, `.h`, `.sp`.

**Misc:** `lib/features/utils.dart` has shared helpers (date formatting, secure-storage `saveData`/`getData`, unit labels). Firebase messaging and local notifications are dependencies used for push notifications.
